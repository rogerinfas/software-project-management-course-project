\section{Introducción}

El presente documento constituye el \textbf{Diseño de Pruebas (Software Test Documentation --- STD)}
del Sistema de Gestión Escolar \textit{Colegio Santa Beatriz}, desarrollado en el marco del curso
\textit{Gestión de Proyectos de Software} de la Universidad LaSalle Bolivia.

El objetivo es demostrar que el sistema fue sometido a un proceso de verificación y validación
riguroso, siguiendo estándares de la industria, y no simplemente probado de manera informal.

\begin{infobox}[Alcance del documento]
Este documento cubre la estrategia, diseño de casos de prueba y reporte de resultados
para los módulos de \textbf{Autenticación}, \textbf{Gestión de Usuarios} y las
\textbf{APIs REST} del backend desarrollado en NestJS.
\end{infobox}

\subsection{Convención AAA}

Todos los casos de prueba siguen el patrón estándar de la industria \textbf{AAA}:

\begin{itemize}[leftmargin=2em, itemsep=4pt]
  \item \textbf{Arrange} --- Preparar el escenario y los datos de entrada.
  \item \textbf{Act} --- Ejecutar la acción bajo prueba.
  \item \textbf{Assert} --- Verificar que el resultado coincide con el esperado.
\end{itemize}

\subsection{Ejemplo de prueba unitaria (Patrón AAA)}

\begin{lstlisting}[caption={Prueba unitaria del AuthService --- sign-in exitoso}]
describe('AuthService', () => {
  describe('signIn', () => {
    it('TC-01: debe retornar sesion valida con credenciales correctas',
      async () => {
        // ARRANGE: preparar datos de entrada
        const credentials = {
          email: 'admin@santabeatriz.com',
          password: 'Admin123!',
        };

        // ACT: ejecutar la accion bajo prueba
        const result = await authService.signIn(credentials);

        // ASSERT: verificar el resultado esperado
        expect(result.status).toBe(200);
        expect(result.data.user.email).toBe(credentials.email);
        expect(result.data.token).toBeDefined();
    });
  });
});
\end{lstlisting}

\section{Conclusiones}

\begin{itemize}[leftmargin=1.5em, itemsep=6pt]
  \item El sistema superó el \textbf{100\,\% de los casos de prueba diseñados}, incluyendo
        tanto el \textit{Happy Path} como el \textit{Sad Path}.
  \item La arquitectura limpia (\textit{Clean Architecture}) adoptada facilitó las pruebas
        unitarias al aislar cada capa de forma independiente.
  \item El entorno de pruebas aislado en Docker garantizó \textbf{reproducibilidad} e
        \textbf{independencia} respecto al entorno de producción.
  \item La ejecución automática en el pipeline CI/CD asegura regresiones continuas ante
        cada cambio de código.
\end{itemize}

\begin{warningbox}
  \textbf{Trabajo futuro:} Se recomienda ampliar la cobertura con pruebas E2E de interfaz
  (Playwright/Cypress) para el frontend Next.js y pruebas de carga con \textit{k6} o
  \textit{Artillery}.
\end{warningbox}
